# 《独家童话》文件与异步任务

本文把[总体架构](./01-总体架构.md)、[API 通用规范](./02-API通用规范.md)、[数据库设计](./03-数据库设计.md)和[模块 API 清单](./04-模块API清单.md)落实为 API 与 Worker 都可执行的流程。API 与 Worker 在同一后端仓库、使用同一领域 Service 和 Prisma 访问层，却是两个独立进程；API 只授权、写入和投递，Worker 不提供业务 HTTP 入口。

本文件只使用已定义的 `files`、`file_upload_sessions`、`file_variants`、`async_jobs`、`ai_jobs`、`ai_job_events`、`works`、`work_assets`、`credit_wallets`、`credit_ledger`、`notifications`、`notification_deliveries` 和各资源所有者表。状态严格沿用数据库字典：不新增表或状态；任何未来表、用途或状态先回补数据库、API 和验收契约。

## 1. 不可变边界

- 二进制只在私有 S3 兼容对象存储；PostgreSQL 不保存二进制，App 不持有对象存储管理凭证，也不能提交 `object_key`。
- `files` 没有独立可见性。下载、缩略图、导出和作品产物都以真实直接引用及递归来源链权限为准；缓存、文件 ID、`reference_count` 均不是授权事实。
- 上传、完成、删除和任务创建均在当前用户、当前有效情侣关系、用途、资源状态与容量约束下授权。旧关系、`DISSOLVING` 关系、已删除资源和未到期胶囊不能得到新签名。
- `ai_jobs` 是工坊业务任务及用户可读事件；`async_jobs` 是其稳定的实际执行、可靠待投递和幂等回执。两者不能混为一个 ID 或以队列内存代替数据库事实。
- 供应商对象存储、病毒扫描、媒体处理、AI、短信、推送和观测均通过适配器接口接入，可替换，不把云厂商 SDK 或原始错误泄露给领域模块或 App。

## 2. 文件对象、上传会话与状态机

### 2.1 服务器生成对象键

申请上传的事务先创建 `files`（`status=UPLOADING`）和唯一 `file_upload_sessions`（`status=PENDING`）。对象键仅由 files Service 生成，例如 `private/{environment}/{fileId}/original`；环境、随机 UUID 和固定角色使不同环境、文件和衍生对象互不冲突，且不含手机号、昵称、情侣 ID、文件名或可猜测序号。该值只写 `files.object_key`，普通 DTO、日志、通知、`async_jobs.response_json` 和客户端请求均不返回它。

`file_variants` 的对象也先由服务器生成，角色限定为 `thumbnail`、`preview`、`transcode` 或 `pdf`，并为其建立自己的 `files` 行；映射以 `(source_file_id, variant_type)` 唯一约束和 `variant_file_id` 唯一约束收口。原始文件和变体必须保持相同 owner/couple 归属，变体不获得更宽的访问范围。

### 2.2 `authorize → PUT → complete`

1. `POST /api/v1/files/upload-sessions` 接受 `UploadInput` 与 `Idempotency-Key`。API 以用途决定 MIME 白名单、字节上限、容量主体和允许的引用上下文；锁定同一容量主体，校验 `checksumSha256` 是 64 位十六进制，并在同一事务创建文件、上传会话和幂等记录。重复键同载荷只在会话仍为 PENDING 且未过期时，才可返回同一 `fileId/uploadId` 的新短期授权；已 complete/session 达终态后不得重新授权写入，重复请求只回放脱敏的既有终态结果。异载荷或进行中的意图按通用规范返回 `IDEMPOTENCY_CONFLICT`，`details.reason=IN_PROGRESS`。
2. API 向对象存储适配器取得仅针对该 `object_key`、方法 `PUT`（或契约允许的 `POST`）、`Content-Type`、最大字节数和到期时间的凭证，响应 `uploadUrl`、受限 headers/fields 与 `expiresAt`。签名必须强制条件创建 `If-None-Match: *`，并把该条件列为不可由客户端移除的受签名请求头/表单条件；对象已存在时存储端拒绝写入，绝不允许同一 object_key 覆盖。`signed URL` 是短期凭证，绝不落库、绝不记录完整查询串，也不放入回执、通知或分享链接。
3. 客户端只执行一次带 `If-None-Match: *` 的受限 `PUT`，不能列表、读取、覆盖其它对象或改变 MIME/长度。条件失败表示对象可能已上传，客户端只能调用 complete 核验，不能申请可覆盖写入的凭证；储存端成功不代表业务文件可引用。
4. `POST /api/v1/files/upload-sessions/{uploadId}/complete` 锁定会话、文件和容量主体，再由存储适配器读取可信元数据：对象存在、实际 `size_bytes`、MIME、强制的 `checksum`/SHA-256 与会话声明完全相符。不得信任客户端“已上传”声明或请求头回显。核验通过后以原子转换 `file_upload_sessions: PENDING/UPLOADED → COMPLETED`、`files: UPLOADING → READY`，写 `verified_at`；已完成重复请求只返回同一 `File`，不重复计算容量或创建变体任务。

会话过期走 `PENDING/UPLOADED → EXPIRED`，用户撤销走 `PENDING/UPLOADED → CANCELLED`，两者均不能再 complete；完成与取消/过期抢同一行锁，最多一个成功。常规 PUT 完成后可先记 `UPLOADED`，但不能给客户端 READY 响应，直到服务端核验完成。这样不引入 `VERIFYING` 或病毒扫描专用任务状态。

### 2.3 上传校验、病毒与图片派生

- 文件用途、声明 MIME、实际 MIME、魔数、实际字节数和 `checksum` 都必须一致；图片解码器还要限制像素、帧数、动画、EXIF 方向和解压后资源用量。双扩展名、伪造 Content-Type、损坏图像、过大文件和超时对象均拒绝并排清理。
- 病毒/恶意内容检测由受隔离的扫描适配器在文件转为 READY 前给出可审计的干净、可疑或不可用结果。命中或可疑时，锁定文件、会话和容量主体的同一事务必须同时执行 `files: UPLOADING → QUARANTINED`、`file_upload_sessions: PENDING/UPLOADED → CANCELLED`、写入 `audit_logs.action_code=FILE_VIRUS_DETECTED`（白名单 metadata 的稳定 `reasonCode=VIRUS_DETECTED`）、创建既有 `FILE_DELETE` 清理任务并完成容量预留释放；QUARANTINED 文件不计入用户可用容量，且不建立 `COMPLETED` 会话、不签名、不允许业务引用。重复 complete 读取已 CANCELLED 会话时只返回同一脱敏的 `File{status:QUARANTINED}`，不再次扫描、写入、计量或重新授权。不可用不以“跳过扫描”放行；隔离对象只允许受控运维取证，随后由该清理任务按保留策略删除，不返回样本、路径或供应商原始结果。
- `READY` 的图片/视频可创建现有 `async_jobs.job_type=FILE_VARIANT`，其 `PENDING → PROCESSING → SUCCEEDED/FAILED/CANCELLED` 只生成 `file_variants` 已定义的 THUMBNAIL/PREVIEW/TRANSCODE/PDF。原图已经可读不因派生失败变为公开；变体失败可重试或退化到经过同一授权的原图，不能把失败的缩略图当作无权限预览。

## 3. 私密下载、引用与清理

### 3.1 签名下载授权

`GET /api/v1/files/{fileId}/download-url` 必须提交受控的 `resourceType/resourceId` 上下文。files Service 先确认 `READY`、未删除、用途与真实直接引用相符，再委托资源所有者 Service 完整复核：

- 头像核对 `users.avatar_file_id` 与本人；情侣封面核对当前 ACTIVE `couples.cover_file_id` 和有效成员；时刻封面同时核对 `important_moments.cover_file_id`、未删除状态与 `moment_record_links` 的来源链。
- 日记/照片、回应附件、胶囊、主角参考、作品资产和回忆册补页依次核对所属资源、作者/当前关系、`PRIVATE/COUPLE`、软删除与用途。封存且未到期的胶囊拒绝正文、`fileId`、缩略图和下载。
- 回忆册、作品、PDF、导出和缩略图递归复核来源链；MOMENT 再核对关联 record，WORK 再经 `ai_jobs → creation_drafts → creation_draft_sources` 核对。来源失效时返回不可用占位或 `FILE_ACCESS_DENIED`，不回退到缓存地址。

成功后才签发最短可用期的 signed URL。它到期前的最大暴露窗口由短有效期承担；需要即时撤销时改走每次请求均鉴权的受控访问代理。资源一旦进入删除或权限收回，停止新签名。任何不匹配的 `resourceType/resourceId/fileId` 组合、越权探测或伪造上下文都不泄露对象存在性。

### 3.2 引用计数、延迟删除与恢复窗口

各数据所有者 Service 在同一数据库事务内创建/移除直接引用并更新 `files.reference_count`；它只用于候选清理，不能代替删除前的真实反向引用检查。文件进入业务软删除恢复窗口时，仍保留元数据且不安排物理删除；恢复窗口结束且计数为零，files Service 锁文件并置 `DELETE_PENDING`、填写 `delete_after/delete_job_id`，创建已有 `async_jobs.job_type=FILE_DELETE`，再提交可靠投递记录。

`FILE_DELETE` Worker 在删除前再次锁定文件、复核所有直接引用、变体、来源链和恢复窗口。任何存活引用、重新使用或尚未到期都会取消此次物理清理并保留文件，不以计数缓存误删；安全隔离的 QUARANTINED 文件只允许其在同一隔离清理任务中到期删除，不能重新使用。确认无引用后按变体优先、原对象最后的顺序幂等删除私有对象；存储报告“已经不存在”也是成功，全部确认后才写 `files.status=DELETED`、`deleted_at` 且 `reference_count=0`。对象失败则按任务重试；元数据确认删除后保留 90 天，上传会话终态保留 90 天。`UPLOADING` 过期、`QUARANTINED` 和业务软删到期对象都使用同一延迟删除机制。

## 4. 可靠队列与 Worker 状态机

### 4.1 事务后投递与补投

生产者在一个 PostgreSQL 事务中写业务记录、`async_jobs.execution_mode=QUEUED,status=PENDING`、稳定 `bullmq_job_id`、所需预扣/回执和审计。提交成功后才尝试以该稳定 ID 投递 BullMQ；数据库和队列绝不假定同一事务。投递失败不回滚已提交业务事实，而保留可查询的 PENDING 行。

API 后台投递器和 Worker/定时扫描器按 `(status, run_after, id)` 领取缺少或失效队列投递的行，使用相同 `bullmq_job_id` 重投；BullMQ 的 jobId 去重和数据库唯一约束使可靠补投安全。扫描器还核对长期 PENDING、过期租约和队列中失踪任务并告警。`execution_mode=RECEIPT` 是同步幂等回执，创建事务内已经终态，永不投递给 BullMQ。

### 4.2 状态、租约、重试与 DLQ

QUEUED 任务唯一状态机为 `PENDING → PROCESSING → SUCCEEDED|FAILED|CANCELLED`；`PROCESSING → PENDING` 只表示可重试技术失败或租约超时后的重新调度，终态绝不回退。Worker 以 `id + version + status` 原子抢占，写 `locked_at/locked_by`、递增 `attempt_count`，并以稳定执行 ID 调用外部适配器。开始、进度、结果发布和终态都重新读数据库，旧尝试、重复 BullMQ 消息或晚到供应商回调无法覆盖新尝试。

每个 job_type 有明确最大次数（默认 `max_attempts=3`，表约束 1–20）、执行超时和指数退避加抖动；只对网络、临时供应商、限流和可恢复存储故障重试。验证、权限、额度、来源失效、病毒隔离和不可恢复格式错误立即 FAILED 或按业务规则 CANCELLED，不能盲目重试。超时释放/过期租约后由扫描器重新调度；Worker 优雅关闭时不领取新任务，并让租约自然恢复或安全释放。

达到次数、不可恢复失败或人工停止后，任务写 `FAILED` 或 `CANCELLED`、`completed_at` 与稳定 `error_code`。BullMQ failed 集合是 DLQ（死信观察）而不是新的数据库状态；告警同时关联 `async_jobs.id`、`bullmq_job_id`、`requestId` 和脱敏错误码。修复后只能由受控操作用原任务语义重新投递或创建被允许的新用户意图，不能手改终态/账本。

### 4.3 进度、事件与通知

Worker 仅把 0–100 的可展示进度和脱敏阶段码写入 `async_jobs`；AI 同时以 `(ai_job_id, sequence)` 追加最近事件到 `ai_job_events`。客户端轮询受权 `Job` DTO，不直接订阅 Redis 或供应商。进度写入使用版本/租约条件，发布产物前再次检查任务仍是当前 `PROCESSING`、账号/关系/来源有效。

成功、最终失败、可操作取消和导出就绪可在同一业务终态事务创建 `notifications`、`notification_deliveries` 与既有 `NOTIFICATION` QUEUED 任务。投递前再次执行通知偏好、静默时段和资源权限；通知正文不含签名 URL、私密正文、对象键或供应商信息。

## 5. AI 积分预扣、结算与补偿

`POST /ai-jobs` 的首次 `Idempotency-Key` 请求锁定钱包，在一个事务内校验草稿/来源链/权益并写 `ai_jobs`、`ai_job_events`、QUEUED `async_jobs`、`credit_ledger.entry_type=RESERVE` 和 `credit_wallets` 缓存。RESERVE 将可用余额减额、冻结余额加额；任务、预扣和幂等回执一起提交，任何一步失败全部回滚。提交后的 BullMQ 失败由可靠补投修复，不能为了“确保投递”创建第二笔预扣。

Worker 成功时，在结果文件已私有登记、作品与资产仍通过来源链复核后，以同一终态事务写业务成功、`SETTLE` 和余额冻结扣减；技术最终失败、已确认取消或无法发布结果时写 `RELEASE`，冻结回到可用。`SETTLE/RELEASE` 都引用原 RESERVE 的 `origin_entry_id`，其部分唯一约束保证只能一个账务终态；普通角色不能直接改钱包或流水。

重试技术失败沿用原 RESERVE 和同一执行语义，绝不再次 RESERVE。任务仍未结算时可复投；已 RELEASE 的任务不允许用 retry 重新扣款，用户必须创建新草稿与新任务。供应商晚到成功、重复回调或旧 Worker 只能在持有当前租约/版本且 RESERVE 未终结时发布；否则清理未登记产物并保持已写终态。余额与流水每日核对，预扣长期未结算、SETTLE/RELEASE 冲突、DLQ、扫描滞留和补投年龄均触发告警与受控人工处置。

## 6. 运维、保留与验收清单

最小监控包括：上传授权/完成失败率、checksum/MIME 拒绝、QUARANTINED 数、无主对象与删除滞留、签名拒绝率、对象存储延迟；队列深度、PENDING 年龄、租约超时、重试、DLQ、处理耗时和补投成功率；AI 成功率、外部调用延迟、预扣未结算金额、SETTLE/RELEASE 对账差异和通知投递率。日志只保留 requestId、内部任务 ID、脱敏目的/错误码和耗时，禁止完整 signed URL、对象键、正文、凭证与供应商原始响应。

每次发布都验证：伪造大小/MIME/checksum 不能 READY；重复 complete 不重复计量；取消与完成互斥；无权上下文不能签名；PRIVATE、关系解除、来源失效和未解锁胶囊不能通过变体/导出泄露；重复 BullMQ 消息和任务超时不重复发布/结算；FILE_DELETE 对已有/已不存在对象均幂等；失败最终只产生一个 RELEASE 或 SETTLE。对象存储生命周期规则只能辅助回收，仍以 Worker 的数据库复核和最终 `DELETED` 记录为准。
